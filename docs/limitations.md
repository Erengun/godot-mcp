# Known limitations

This page lists what godot-mcp 2.0 does not do, does only partly, or does with caveats. Each entry says why.

## Engine and headless constraints

- **Scene editing runs some script code.** Headless editing instantiates the scene, so the `_init()`, `_notification()` (for example parenting and deletion), property setters, `_set()`/`_get()`, `_get_property_list()` and `_validate_property()` of attached scripts run, and so do those of scripted sub-resources (including `_setup_local_to_scene()`). `godot_resource_edit` and `godot_resource_inspect` run the same methods of a scripted resource. `_ready`, `_process` and other tree callbacks never run, and neither do the autoloads. Loading any GDScript also runs its `static var` initialisers and `_static_init()`, including those of the autoload scripts it refers to. A thread that project code starts keeps running until the worker process ends, right after the operation. If you need zero execution, use the live editor bridge, which uses the editor's placeholder instances for non-tool scripts.
- **Scripts that use autoload singletons.** The headless worker registers every autoload name with an empty placeholder node, so scripts that use autoloads compile and are validated, edited and saved like any other script, but the autoloads themselves never run.
  - Code that runs during an edit (see the previous entry) sees the placeholder, so a line that uses an autoload fails there. When that changes a stored value, the save is refused (see "Saves are compared with the original").
  - The analyzer types a scene autoload (`Hud="*res://hud.tscn"`) as a plain `Node`, not as the class of the scene's root script. Code that relies on that class, such as `var x := Hud.method()` or `return Hud` from a function typed with it, is therefore reported as an error headlessly, and scenes that use such a script cannot be edited headlessly. The editor and the game are not affected.
- **Files that cannot be loaded completely.** Godot loads a scene or resource without the parts it cannot load and would save it that way. Writes are therefore refused with `OPERATION_FAILED`, and the file is left untouched (`godot_uid resave` lists it under `skipped`), when the file uses:
  - a script that does not compile or load: scripts with errors, built-in scripts with errors, and C# scripts without a .NET build of Godot;
  - a direct dependency that is missing or not imported yet (run `godot_import` first);
  - a node or resource class that is not available, such as one from a GDExtension that is not loaded.

  Fix the cause, or make the change in the editor (`godot_editor`).
- **Saves are compared with the original.** Every headless save (and every `dryRun`) is compared with the file it was loaded from, as text; binary scenes are compared through a temporary text copy. Apart from what the actions explain:
  - every stored value in every node, sub-resource and resource section must be unchanged, and no value may be added (also not in an override section the save gains for a node of an inherited or instanced scene); instances keep their editable-children setting;
  - no node, instanced scene, node type or signal connection may disappear, and nodes keep their groups and their order among their siblings (under a node from an inherited or instanced scene, the order that the stored `index` values produce when Godot loads the file), and connections keep their flags, binds and unbinds;
  - a node that `duplicate_node` created, and each of its children (followed through later renames and moves), must store the same values and groups as its source (only nodes the edited file defines in full can be copied: see Known gaps), apart from what actions set on the copy (and the layout of a Control copied under another parent). The copy must have exactly its source's children, in the same order, and the connections from its source's nodes (Godot does not copy connections that other nodes make to them), apart from what actions add to, remove from or reorder in the copy. A batch that changes the source (or a node below it) after copying it is refused: setting values (also through a move that re-lays out a Control or keeps the global transform), re-scripting, regrouping, toggling editable children, connecting or disconnecting its signals, or removing it, because the copy can then no longer be checked: copy in one call and change, move or remove the original in the next. A Container does not store some values of its children (a Control's `rotation`, `scale`, `pivot_offset`…), so copying or moving a Control that stores them into a Container is refused;
  - no other node or connection may appear.

  A stored value may only disappear when the object still holds it as a stored property, which means it equals the default and Godot's saver omits it. It may also disappear when it is no longer a property at all: an obsolete key that Godot drops or renames when it upgrades a file. A key the save gains in its place is accepted only when Godot itself makes it from the obsolete one: a sub-key of it (such as `libraries/` from `libraries`), or a key that setting the obsolete value on a new object of the same engine class (without project code) changes. Godot upgrades files from older versions when it loads them, for example by renaming keys or changing how a value is encoded. To accept those upgrades, the worker also re-saves the original right after loading it, before anything is instantiated. A difference in native (non-script) data that this re-save shows too is accepted. In files that contain scripted resources, whose scripts already run while the file loads, this exception does not apply. Script values, metadata and scripted resources are always held to the original. If anything else changed, nothing is written and the operation fails with `OPERATION_FAILED`. (The comparison runs on a temporary copy before the file is written; if the written file differs from that copy beyond resource ids, it is compared again and the original restored on failure.)
  - **What counts as explained:**
    - the properties an action names, including `a:b` paths into a sub-resource (only that key of the sub-resource: the property `a` must still hold the same sub-resource, shared as before, with its other keys unchanged); setting a node's placement (position, rotation, scale, size, anchors…) also covers the other keys Godot stores it under;
    - the native data of the node an authoring action edits (animation, TileMap, GridMap) and of the sub-resources that node holds (for an AnimationPlayer, all animations in its libraries); its script values and metadata are still compared;
    - the layout keys (`offset_*`, `anchor_*`, `size`, `position`…) of Controls that `move_node` moved, and the transform of nodes moved with `keep_global_transform` (setting `position` of a 3D node covers only the origin of its stored `transform`; `rotation`/`scale` cover the whole `transform`);
    - the group that `add_to_group`/`remove_from_group` added or removed;
    - the place among its siblings of the node that `move_node`/`reparent_node`/`reorder_node` placed (the other siblings must keep their order), and, under a node from an inherited or instanced scene, the order of the children of a parent that gained, lost or reordered children;
    - the connection that `connect_signal`/`disconnect_signal` added or removed, matched by signal, method and both ends;
    - removed nodes;
    - nodes an action creates (with their children for `duplicate_node`, which are compared with their source as above), and the overrides of an instance whose editable children an action turned off (a call that leaves the setting as it was explains nothing);
    - what Godot itself restates in an override section the save gains (a node of an inherited scene or of an editable instance that had none): the values the scenes defining that node already store, its own copy of a resource that is local to the scene (compared with the text of the file that defines the original, nested resources included; a script-backed one, or one whose original is in a binary file, is refused), and the `[editable]` lines of the `.tscn` scenes the edited one inherits or instances, and of the scenes those inherit (a binary `.scn` base cannot be read, so those edits are refused: open and save the scene in the editor once);
    - which stored values share a sub-resource is compared too, whatever ids the save gives them: values that shared one in the original must share one in the save, and no others; each copy Godot makes of a resource local to the scene must be the only copy of that resource in the file, and must not also stand for a sub-resource the original stored;
    - on a node whose script an action attached or detached, its script and script values (its native values must stay);
    - renamed and moved nodes, which are followed.
  - **Known gaps and refusals:**
    - In a batch that removes, renames or moves nodes, a node-typed export must point to the same node as before (its path is worked out again; null when that node was removed), and a plain `NodePath` must keep its text; the rest of such a value is compared as usual. `rename_node`/`move_node` update node-typed exports and connections (and `remove_node` clears node-typed values that point at the removed nodes, and removes dictionary entries whose node key it was, listing them as `cleared_references`; when that would bring back a value the inherited scene defines, the save is refused instead), but not plain `NodePath` values (for example `focus_neighbor_*`, `Array[NodePath]`, the track paths of an animation), which keep pointing at the old name.
    - A setter for one property that changes another stored value makes the save fail, even when that is intended.
    - A sub-path (`material:blend_mode`) into a sub-resource that another scene stores (the scene an inherited scene is based on, or an instanced scene) is refused with `CONFLICT`, because the edited scene does not store it and the change would be lost. Change it in that scene, or assign a new resource to the property.
    - When two connections have the same signal, ends and method (differing only in binds or flags), Godot loads only one of them, so every save of such a file is refused (the other one would be dropped). Remove the duplicate in the editor.
    - A Control that a hand-written file stores without `layout_mode` gains it on save; that is accepted.
    - `duplicate_node` refuses (at save) to copy a node that an inherited scene defines or that belongs to an instanced scene (an editable child): the file stores only its overrides, so the copy cannot be checked. Copy those in the editor (`godot_editor`). Nodes the edited file defines itself, including nodes an inherited scene adds and whole instances (with or without editable children), can be copied. Godot's duplicate does not carry the groups that this file adds to an instance's own (editable) nodes, so copying such an instance is refused too.
    - Scenes with `instance_placeholder` nodes and Godot 3 (`format=2`) files are refused.
    - A resource that is local to the scene and held in a script variable (or an array of them) of a node from an inherited scene makes every save of the inheriting scene fail; edit such scenes in the editor. Held in a native property (such as `material`), it is accepted.
    - A `String` and a `StringName` with the same text compare as equal, and so do an `int` and a `float` with the same value and a typed collection (`Array[int]`, `Dictionary[String, int]`) and an untyped one with the same contents, so a save in which project code changed only such a type is accepted.
    - When the save would add copies of one resource that is local to the scene for more than one scene in the file (two instances of the same scene, or a node a scene adds under an instance), it is refused: which of those copies Godot shares differs between Godot versions, so it cannot be checked. Files the editor saved already store these copies and are not affected; open and save such a scene in the editor once.
    - An `[editable path]` line for a node inside an instance whose own children are not editable is dropped by Godot, so every save of such a (hand-written) file is refused.
- **`saveAs` targets.** `godot_scene_edit` with `saveAs` (and the legacy `save_scene` with `newPath`) refuses a target that the scene, as edited, depends on, such as a scene it instances (also one the batch instanced or assigned to a property), because the copy would replace it and refer to itself. `godot_scene_edit` also refuses an existing target unless `overwrite: true` is passed; the legacy `save_scene` with `newPath` always replaces an existing target, as it did upstream.
- **Setting a property whose setter fails.** When a project script raises an error while `set_properties` (or `godot_resource_edit`, `attach_script` properties) sets a value, the action fails with `OPERATION_FAILED` and nothing is saved, because the value may not have been stored.
- **Binary scenes and resources with scripted resources.** In a `.scn` or `.res` file, the values of scripted sub-resources (or of a scripted `.res` itself) pass through their scripts when the file loads, and nothing records what the file held. Writes to such files are refused. Save them as `.tscn`/`.tres`, or edit them in the editor. `godot_uid resave` re-saves only `.tscn` and `.tres` files.
- **Inherited scenes can't be created through the public API.** Packing a `GEN_EDIT_STATE_MAIN_INHERITED` instance flattens it. `godot_scene_create {inherits}` therefore writes the minimal documented `.tscn` header (`instance=ExtResource`) and then has Godot load, re-pack, re-save and verify it.
- **UIDs in references.** Outside the editor, Godot's text saver writes `[ext_resource]` lines without the `uid="…"` attribute. After every save, the worker re-inserts the UID of each referenced file. Only that attribute is inserted; the result is re-verified. The worker also registers all project UIDs at startup, so `uid://` references resolve without an editor-built cache.
- **Ext-resource ids get renumbered.** Godot regenerates `ext_resource` ids (`id="1_abcd"`) when it re-saves a scene. Semantic content is preserved, but the text diff of an edited scene includes those id changes. Fixture D verifies that nothing else changes.
- **`ProjectSettings.save()`** re-sorts sections, drops comments in `project.godot` and writes `config/features` for the running engine version, the same as saving in the editor. A backup is kept in `.godot/godot_mcp/backups/`.
- **Class cache refresh starts the editor.** New `class_name` scripts need the global class cache. `godot_script_write` refreshes it automatically with `godot --headless --import`, which starts the editor and runs editor plugins and `@tool` scripts. Turn this off with `refreshClassCache: "never"`.
- **Navigation meshes are not baked headlessly.** Baking needs a SceneTree and the NavigationServer. Bake at runtime (`NavigationRegion3D.bake_navigation_mesh`, see Fixture B) or in the editor.

## Visual capture

- **No capture of an already-running game.** `godot_screenshot` renders the scene in a *fresh* process with the GPU renderer. Capturing the window of a game started earlier, or the editor viewport, would need cooperation from inside that process (an injected autoload or the debugger protocol), and that is not implemented.
- **A display is required.** Headless Linux CI needs `xvfb-run` or a similar virtual display. Without one, the tool returns `CAPABILITY_UNAVAILABLE` and never produces a fake image.
- **Visual checks are partial.** The automated checks are a blank-image check, colour variety, missing meshes or textures, meshes inside the camera frustum and the presence of cameras and lights. Judging aesthetic quality requires looking at the returned image.

## Debugging

- **Log-based diagnostics only.** Runtime diagnostics are parsed from Godot's console output: `SCRIPT ERROR`, `ERROR`, `WARNING`, `USER ERROR` and `SHADER ERROR`, with `at:` locations and GDScript backtraces.
- **No debugger integration.** The GDScript Debug Adapter Protocol, the remote debugger protocol and the language server are **not** integrated. Breakpoints, stepping and variable inspection are not available.
- **No `-d` flag.** Games are started without `-d`, because the stdout debugger blocks on stdin at the first error.

## Live editor bridge

- **Plugin required.** The bridge only works after the plugin is installed and enabled in the project and the editor has been (re)started. If you enable it while the editor is already running, the editor may overwrite the setting.
- **Limited live operations.** Live operations cover status, tree, selection, open, save and reload of scenes, `set_properties`, `add_node`, `remove_node`, filesystem scan, play and stop, and editor-side errors. Batched structural edits (reparent, instancing, animation, TileMap) are headless-only.
- **Same-user access.** Other processes running as the same OS user can read the token file (see security.md).

## Platform and version coverage

- **Tested environment.** The full suite passes on macOS (local M3 and CI macos-14), Ubuntu 24.04 and Windows Server 2022 with Godot 4.7.2, and on Ubuntu with Godot 4.8 beta 2. Other distributions, Linux arm64 and Windows desktop editions are not covered.
- **Godot < 4.5.** Not supported. The worker relies on `Logger` / `OS.add_logger`, which arrived in 4.5.
- **C# / .NET.** `godot_dotnet build` (`dotnet build` plus MSBuild diagnostics) is implemented but unverified, because no Godot .NET build was available. C# scripts are skipped by GDScript validation, and reflection is GDScript-only.

## Not implemented

- **Input and gameplay automation.** There is no simulated input or automated gameplay driving beyond the project's own scripts and `--quit-after`.
- **3D asset pipelines.** glTF / Skeleton3D / AnimationTree authoring is not covered. Generic property editing works on these nodes, but no dedicated workflows exist or have been tested.
- **Shader-specific tooling.** `.gdshader` files can be written and validated as resources, but there is no shader-specific parse report.
- **Third-party plugin APIs.** Not covered.
- **Main scene required.** `godot_project_validate` reports a missing main scene as an error, so library-style projects without a main scene read as unhealthy.
